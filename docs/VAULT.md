# Master password vault

TermiPaw never stores passwords in plain text. A password or private key passphrase can only be saved in the vault, an encrypted file protected by a master password that you choose. While the vault is off, nothing is saved and you enter the password each time you connect.

The vault can also encrypt the host list itself, so that the data folder does not reveal which servers you connect to.

This document describes what the vault protects against, how it works, and its limits. The file format is fixed once released, so it is specified here in detail.

## What it protects against

| Situation | Vault off | Vault locked | Vault unlocked |
| --- | --- | --- | --- |
| Someone uses your unattended, logged-in computer | No saved passwords to use | **Cannot connect with saved passwords** | Can; automatic locking shortens this window |
| Someone copies the data folder or a backup | No passwords in the files | Can only guess the master password offline | Same |
| Another Windows account on the same computer | Cannot read the files if folder permissions are set accordingly | Same | Same |
| Malware running as your user | No saved passwords | Cannot read passwords, but can copy the file to guess offline, or log keystrokes while you type the master password | **Can read process memory** |

In short:

- The vault mainly protects against **someone using the computer** and **files being taken**. If the computer already runs malware, the vault only protects until the next unlock.
- With a weak master password, offline guessing is feasible. The length of the master password and the cost of Argon2id are what stand in the way.
- If you forget the master password and have no recovery key, the contents **cannot be recovered**.

**Out of scope:**

- An attacker who can replace the program or put back an older vault file. Someone with that level of access can do worse.
- Inferring the amount of content from the file size.
- Old data already written to disk. SSDs and system backups may still hold earlier plain-text files; TermiPaw cannot guarantee they are erased.

## Key structure

```
master password ──NFC──> Argon2id ──> wrapping key ──┐
                                                     ├─ unwraps ──> data key (random, 256 bits) ──> encrypts the contents
recovery key ──────────> Argon2id ──> wrapping key ──┘
```

- **Data key:** generated by the system random number generator. Only this key encrypts the contents.
- **Slots:** one per unlock method (master password, recovery key). Each holds a wrapped copy of the data key, so the recovery key does not need its own copy of the contents.
- **Cipher:** XChaCha20-Poly1305 with a fresh random 24-byte nonce for every encryption.
- **Argon2id parameters:** 256 MiB of memory, 3 iterations, parallelism 1, 32-byte output, 16-byte salt. Unlocking takes about 0.4 seconds on a recent desktop CPU and is expected to take a few times longer on older laptops. Parallelism is 1 because the `argon2` crate computes on a single thread, so higher parallelism would only slow down the user while an attacker could still parallelize.

**Master password rules:**

- At least 8 characters, counted as Unicode characters after NFC normalization. No composition rules. Eight characters is the common minimum (NIST SP 800-63B uses the same minimum for user-chosen passwords); the interface still recommends a longer password, because length is what resists offline guessing.
- Leading and trailing spaces are kept.
- NFC normalization makes the same visible text produce the same bytes regardless of keyboard or input method. It is part of the format and cannot change.

**Recovery key:** 128 random bits, shown once as 26 Crockford Base32 characters in groups. Input is case-insensitive and ignores separators. It goes through the same derivation as the master password.

**No attempt limit:** Argon2id already limits the guessing rate, and a counter in the interface would not stop offline guessing. Unlock requests are processed one at a time so they cannot exhaust memory.

## File format

The vault is `vault.json` in the data folder. Like the other configuration files it is written atomically (temporary file, `sync_all`, rename).

```json
{
  "format": "termipaw-vault",
  "version": 1,
  "revision": 17,
  "encryptMetadata": false,
  "slots": [
    {
      "type": "password",
      "kdf": { "name": "argon2id", "version": 19, "memoryKib": 262144, "iterations": 3, "parallelism": 1 },
      "salt": "<base64>",
      "nonce": "<base64>",
      "wrappedKey": "<base64>"
    }
  ],
  "nonce": "<base64>",
  "ciphertext": "<base64>"
}
```

Decrypted contents:

```json
{
  "secrets": { "<host id>": "<password or passphrase>" },
  "idleMinutes": 15,
  "hosts": null,
  "knownHosts": null,
  "uploadTemps": null
}
```

The last three fields are only filled when host information is encrypted. Files written by versions before 0.7.0 may contain a `keyringCleanup` field; it is read and ignored.

**Tamper protection:** the following values are bound to the ciphertext as associated data, in a fixed length-prefixed byte layout rather than re-serialized JSON:

- Slots: `termipaw-vault-slot-v1`, slot type, KDF parameters, salt.
- Contents: `termipaw-vault-data-v1`, `revision`, `encryptMetadata`.

Changing a parameter or a flag therefore makes decryption fail.

**Checks when reading:**

- Wrong `format`, or a `version` newer than the program: refused without changing the file.
- KDF parameters outside 64 MiB–1 GiB memory, 1–10 iterations or parallelism 1–4: refused, so a modified file cannot exhaust memory.
- A slot that does not open can only be reported as "wrong master password, or the file was modified"; the two cannot be told apart.
- A slot that opens but contents that do not decrypt: reported as a damaged file.

**Parameter upgrades:** after a successful unlock, a password slot with weaker parameters than the current defaults is re-wrapped. The recovery key slot cannot be upgraded this way, because the program never keeps the recovery key.

## Keys in memory

- After unlocking, only the data key is kept in memory (zeroized when dropped). The contents are decrypted when needed and zeroized afterwards. Locking clears the data key.
- **No command returns a decrypted password to the interface.** The interface can only ask the backend to connect to a saved host, and the backend checks that the connection target matches that host before using its password.
- **Limits:** the master password is typed in the WebView, and JavaScript strings cannot be zeroized; copies inside the SSH library are out of reach; memory pages may be written to the page file or the hibernation file.

## Turning the vault on and off

- **Turning on:** the vault starts empty. Hosts that older versions marked as having a saved password lose the mark, and you are told which ones. The new file is written, read back and verified before the vault counts as on.
- **Turning off:** requires the master password even when unlocked. Passwords saved in the vault are **deleted**; they are not moved anywhere else. If host information was encrypted, it is first written back to the plain-text files, and the vault file is only removed after that succeeds.

## Changing the master password

A new data key is generated and all contents are re-encrypted. If a recovery key exists, a new one is issued and the old one stops working.

Re-wrapping the existing data key would be simpler, but someone holding an old copy of the file who later guessed the old master password could then read new contents too. People usually change the master password because they suspect it leaked, so the data key always changes.

An old copy of the file together with the old master password still opens the contents of that time. If you suspect a leak, change the server passwords as well.

## Forgotten master password

- **With a recovery key:** unlock with it and set a new master password in the same step.
- **Without a recovery key:** the only option is to reset. `vault.json` is moved to a timestamped backup, and TermiPaw continues as if the vault were off. Saved passwords have to be entered again.
- A reset requires typing a confirmation word in the current language, checked by the backend. The backup is kept in case you remember the master password later.

If host information was encrypted, a reset also loses the host list and the trusted host keys. Every connection afterwards is treated as a first connection, and the interface says so before resetting.

## Locking

The vault locks:

- when you choose **Lock now**;
- after a period without keyboard or mouse activity in TermiPaw (5, 15, 30 or 60 minutes, or never; 15 by default);
- when Windows locks;
- before the computer sleeps or hibernates.

System events come from session notifications (`WTSRegisterSessionNotification`) and power notifications (`WM_POWERBROADCAST`). As a fallback, the wall clock is checked every 5 seconds; a jump of more than 60 seconds is treated as sleep. TermiPaw starts locked when the vault is on.

While locked, the whole window is covered by the lock screen. Backend checks are a second line of defence for operations that happen at that moment.

| Feature | While locked |
| --- | --- |
| Connected sessions | Stay connected; output keeps arriving |
| Running transfers | Continue |
| Files open in local programs | Changes are still uploaded |
| New connections that need a saved password | Wait for unlocking |
| Saving a new password | Requires unlocking |
| Deleting a host with a saved password | Requires unlocking, so the password does not stay in the vault as an orphan |
| Automatic reconnection that needs a saved password | Pauses until unlocked, without opening a dialog |
| Automatic reconnection with an agent or an unencrypted key | Continues, unless host information is encrypted (trusted host keys are unavailable) |
| Files dropped onto the window | Ignored |
| Keyboard shortcuts | Disabled |

Two rules prevent data loss when host information is encrypted and the vault is locked:

1. **Saving hosts is refused.** The in-memory host list is unavailable, and an empty list must never overwrite real data.
2. **Host key checks return "locked", not "unknown".** Otherwise every server would look like a first connection and the "host key changed" warning would be lost.

Unavailable data is represented as `None`, never as an empty list, so "unavailable" cannot be mistaken for "empty". Both rules have dedicated tests.

## Encrypting host information

When turned on, these files move into the vault and the plain-text files are deleted:

| File | Contents |
| --- | --- |
| `hosts.json` | Addresses, user names, private key paths |
| `known_hosts.json` | Addresses and ports you connected to, with their host keys |
| `upload_temp_files.json` | Server addresses and remote paths of interrupted uploads |

- TermiPaw must be unlocked before anything can be shown, because the host list is in the vault.
- Records of upload temporary files cannot be written while locked; they stay in memory and are written after unlocking. If TermiPaw crashes in between, a leftover `.part` file on the server is not cleaned up automatically. The target file is not affected.
- The vault is authoritative: plain-text files left over from an interrupted change are deleted after unlocking.
- Existing `*.bak-*` backups of these files are listed when encryption is turned on, and you decide whether to delete them. They may be your only backups.

**Still in plain text:**

- Working copies of remote files open in local programs (the editor must be able to read them).
- Your own `~/.ssh/known_hosts` and private key files.
- `editor.json` (the path of the program you chose) and interface settings (checked to contain no host information).

## Two TermiPaw windows at once

Nothing prevents running two instances, so both may write the vault. Every write:

1. takes a file lock (`vault.lock`);
2. reads the current `vault.json` again;
3. decrypts it with the data key held in memory, applies the change and writes it back with `revision` incremented;
4. if the file can no longer be decrypted (the other instance changed the data key), gives up and switches to the locked state.

Known limits: locking one instance does not lock the other, and the host list is written as a whole, so when both instances edit hosts the later write wins.

## Testing

- **Fixed sample:** a version 1 `vault.json` and its master password are committed; the tests must always open it, so an accidental format change fails.
- **Tampering:** every byte of every part of the file is modified in turn; the result must be an error, never wrong contents or a crash.
- **Fuzzing:** random structures and out-of-range parameters neither crash nor allocate excessive memory.
- **Normalization:** the NFC and NFD forms of the same text open the same vault.
- **The two data-loss rules above**, master password changes, and concurrent writes from two instances.
- **End-to-end:** turning on, connecting, locking, unlocking, changing the master password, recovering, resetting and turning off, with sessions, transfers and file uploads continuing while locked.

Unit tests use cheap KDF parameters; the program, including debug builds and end-to-end tests, always uses the real ones. Automated tests never lock the screen or sleep the computer; they send the real window messages to the window. Registering for the notifications (`WTSRegisterSessionNotification`) can only be verified by locking the screen for real.
